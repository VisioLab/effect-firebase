# Using Vite+, the Unified Toolchain for the Web

This project is using Vite+, a unified toolchain built on top of Vite, Rolldown, Vitest, tsdown, Oxlint, Oxfmt, and Vite Task. Vite+ wraps runtime management, package management, and frontend tooling in a single global CLI called `vp`. Vite+ is distinct from Vite, and it invokes Vite through `vp dev` and `vp build`. Run `vp help` to print a list of commands and `vp <command> --help` for information about a specific command.

Docs are local at `node_modules/vite-plus/docs` or online at https://viteplus.dev/guide/.

## Built-in Commands vs Scripts

`vp <name>` runs a built-in command. `vp run <name>` runs a `package.json` script or a `vite.config.ts` task. Scripts cannot overwrite built-ins, so `vp dev` and `vp run dev` may do different things. Check `package.json` and `vite.config.ts` first, and run `vp run <name>` when the project defines a script or task with that name.

## Running Scripts

Run TypeScript and JavaScript files with `vpx <file>`, for example `vpx ./scripts/seed.ts --dry-run`. It handles enums, decorators, JSX, and tsconfig `paths`, so do not add `tsx` or `ts-node` to run scripts. `vpx --watch <file>` reruns the file when a file it uses changes, in place of `tsx watch`. `vp node <file>` runs plain Node.js.

## Tool Versions

Run `vp toolchain` to show versions and relationships in the active Vite+
release. Add a tool name to select part of the graph. For example, run
`vp toolchain vite`. Use `--global` to ignore the local `vite-plus` package. Use
`vp why <package>` to show the package-manager dependency graph.

## Review Checklist

- [ ] Run `vp install` after pulling remote changes and before getting started.
- [ ] Run `vp check` and `vp test` to format, lint, type check and test changes.
- [ ] Check if there are `vite.config.ts` tasks or `package.json` scripts necessary for validation, run via `vp run <script>`.
- [ ] If setup, runtime, or package-manager behavior looks wrong, run `vp env doctor` and include its output when asking for help.

## Project Review Checklist

The checklist above is regenerated by `vp config` on every `vp install`, so project additions live here.

- [ ] Run `vp run check` in place of `vp check`. The task runs `astro check` on `apps/website` first, which type-checks its `.astro` files and generates the `astro:content` types that `vp check` fails without on a fresh checkout.
- [ ] Run `vp run test-types` next to `vp run check` and `vp test` to run the TSTyche type tests in each package's `typetest/` folder.
- [ ] Write a negative type test as `// @ts-expect-error <message fragment>` directly above the bad statement (prefix it with `void` if it is an Effect or Stream), not as `toRaiseError`: `vp check` type-checks `typetest/` too and would report the error, while TSTyche still matches the fragment against the suppressed diagnostic.

## Doc comments

The API reference on the website (`apps/website`) is generated from the JSDoc of every public module, including the documented members of exported interfaces and classes. Write each export's comment the way Effect writes its own (see `node_modules/effect/src/Effect.ts`), in this order:

````ts
/**
 * One-sentence summary of what it is or does.
 *
 * **When to use**
 *
 * Use to … / Use when … — one or two sentences on when to pick this over the alternatives.
 *
 * **Details**
 *
 * Behaviour, edge cases, failure modes, short paragraphs. Leave out for simple exports.
 *
 * @example Writing a document
 * ```ts
 * import { Effect } from "effect";
 * import { Firestore } from "@visiolab/effect-firebase/firestore";
 * // …
 * ```
 *
 * @see {@link addDoc} for writing under an id Firestore picks
 *
 * @stability unstable
 * @category constructors
 * @since 0.2.0
 */
````

- Write plainly and directly: short sentences, "Use to …", "Fails with …", "Returns …". No run-on explanations of why the types are shaped the way they are; put design rationale in an ADR or an ordinary `//` comment.
- Add **When to use** to every function, constructor, schema and service that has a sibling a reader could reach for instead. Plain models, options and internal helper types only need a summary and Details.
- Link every similar or opposite API with `@see {@link Target} for <how it differs>`, one tag per link, in both directions. Link with `{@link Module.export}` across modules and `{@link Interface.member}` for a member.
- Give `@example` a title after the tag and a fenced `ts` block with full imports from the packages' public entry points. Examples must type-check: try each one in a scratch file inside the package before committing.
- Every public export keeps `@since`, `@category` and `@stability`.
