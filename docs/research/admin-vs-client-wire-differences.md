# Where admin and client Firestore differ on the wire

Research for [#264](https://github.com/VisioLab/effect-firebase/issues/264), under the map [#259](https://github.com/VisioLab/effect-firebase/issues/259) (Effect-native Firestore engine).

Question: what differs between how the Admin SDK and the client SDK talk to Firestore? Transactions, security rules and which credentials bypass them, `readTime` reads, `preferRest`, request headers, limits, and anything else the engine must vary by credential or caller.

Versions read: `firebase-admin@14.5.0` → `@google-cloud/firestore@9.1.0` (+ `@google-cloud/firestore-api@0.2.0` for the generated GAPIC client), and `firebase@13.0.0` → `@firebase/firestore@4.18.0`. The protos are the copies shipped in `@google-cloud/firestore@9.1.0/build/protos/google/firestore/v1/`.

Path shorthands used below:

- **`[admin]/`** = `node_modules/.pnpm/@google-cloud+firestore@9.1.0_supports-color@7.2.0/node_modules/@google-cloud/firestore/build/src/` (compiled from [googleapis/nodejs-firestore `dev/src/`](https://github.com/googleapis/nodejs-firestore/tree/main/dev/src)).
- **`[gapic]/`** = `node_modules/.pnpm/@google-cloud+firestore@9.1.0_supports-color@7.2.0/node_modules/@google-cloud/firestore-api/build/src/`.
- **`[proto]/`** = `node_modules/.pnpm/@google-cloud+firestore@9.1.0_supports-color@7.2.0/node_modules/@google-cloud/firestore/build/protos/google/firestore/v1/`.
- **`[fbadmin]/`** = `node_modules/.pnpm/firebase-admin@14.5.0_@firebase+app-compat@0.5.19_@firebase+app@0.16.3_supports-color@7.2.0/node_modules/firebase-admin/lib/`.
- **`[js]/`** = [`firebase/firebase-js-sdk` at tag `@firebase/firestore@4.18.0`, `packages/firestore/src/`](https://github.com/firebase/firebase-js-sdk/tree/%40firebase/firestore%404.18.0/packages/firestore/src) (TypeScript source; line numbers refer to that tag).

## Summary

- **Who may open a server-side transaction is decided by the credential.** The proto says: "Firestore does not allow 3rd party auth requests to create read-write transactions" (`[proto]/common.proto` l. 60–62). A Firebase Auth ID token is such a third-party credential. That is why the client SDK never sends `new_transaction`/`BeginTransaction` and instead emulates transactions with write preconditions.
- **Admin read-write transactions** start lazily inside the first read (`new_transaction: { read_write: {} }` on `BatchGetDocuments` / `RunQuery` / `RunAggregationQuery`), reuse the returned transaction id for later reads and the `Commit`, retry with `read_write.retry_transaction = <previous id>`, and send a best-effort `Rollback` on failure. The SDK never calls `BeginTransaction` (`[admin]/transaction.js` l. 522–566, 378–446).
- **Client transactions** are optimistic: plain `BatchGetDocuments` without a consistency selector, then a single `Commit` with no `transaction` field whose writes carry `update_time` / `exists` preconditions, plus a `verify` write for every document read but not written (`[js]/core/transaction.ts` l. 63–195).
- **Locking vs optimistic is no longer a pure SDK property.** For server libraries it follows the database's concurrency mode (Standard edition defaults to `PESSIMISTIC`, Enterprise to optimistic). The mobile/web SDKs are always optimistic, whatever the database setting ([Transaction data contention](https://firebase.google.com/docs/firestore/transaction-data-contention)).
- **Read-only transactions and `readTime` reads exist only in the Admin SDK** (`readOnly: true`, optional `readTime`). The client SDK exposes neither. On the wire they are `new_transaction: { read_only: {} }` or a bare `read_time` consistency selector, which the protocol accepts on every read RPC.
- **Security rules are bypassed by the credential, not by the SDK.** Requests with a Google OAuth 2.0 token (service account / ADC) are authorized by IAM and ignore rules. Requests with a Firebase ID token, or with no token, are evaluated against rules ([REST API docs](https://firebase.google.com/docs/firestore/use-rest-api)). Against the emulator, the Admin SDK sends `Authorization: Bearer owner`, which the emulator treats as admin (`[admin]/index.js` l. 1228–1240).
- **Headers differ by SDK.** Both send `google-cloud-resource-prefix` and `x-goog-request-params`. Only the client sends `X-Firebase-GMPID`, `x-firebase-appcheck`, an API key (`?key=` or `x-goog-api-key`) and `Content-Type: text/plain`. `x-goog-api-client` is `gl-js/ fire/<v>` or `gl-node/<v> fire/<v> grpc/<v>` for the client, and `gccl/<v> fire/<admin v>` (plus gax/grpc parts) for the admin.
- **`preferRest`** is an Admin SDK setting: unary RPCs go over HTTP/1.1 REST (google-gax fallback) until a method that needs gRPC is called, which is only `Listen` (`[admin]/index.js` l. 476–488, 512–548). The protocol makes `Listen` and `Write` gRPC- or WebChannel-only (`[proto]/firestore.proto` l. 204–220).
- **The 500-write limit on `Commit` is gone** server-side since March 2023 ([release notes](https://docs.cloud.google.com/firestore/docs/release-notes)). The client SDK's doc comments still say 500 (`[js]/lite-api/write_batch.ts` l. 274–275, `[js]/lite-api/transaction.ts` l. 277). The 10 MiB request size and the 270 s / 60 s-idle transaction limits remain ([quotas](https://firebase.google.com/docs/firestore/quotas)).

## 1. Transactions

### 1.1 Admin SDK (`@google-cloud/firestore`)

**Starting a transaction.** There is no `BeginTransaction` call anywhere in the hand-written source (only the generated GAPIC client has the method). The first read of an attempt passes `TransactionOptions` as the read's consistency selector:

```js
// [admin]/transaction.js l. 540–562
const opts = {};
if (this._writeBatch) {
  opts.readWrite = this._prevTransactionId ? { retryTransaction: this._prevTransactionId } : {};
} else {
  opts.readOnly = {};
}
const resultPromise = resultFn.call(this, param, opts);
this._transactionIdPromise = resultPromise.then((r) => {
  /* r.transaction, else throw */
});
```

The read RPCs map it to `new_transaction` (`[admin]/document-reader.js` l. 107–115: `Uint8Array` → `transaction`, `Timestamp` → `read_time`, otherwise → `new_transaction`). The server answers with the transaction id in the first response (`BatchGetDocumentsResponse.transaction`, `[proto]/firestore.proto` l. 497–499; `RunQueryResponse.transaction`, l. 613–616). Later reads in the attempt wait on that id and send it as `transaction` (`[admin]/transaction.js` l. 523–530).

**Reads.** `Transaction.get` takes a `DocumentReference`, a `Query` or an `AggregateQuery` (`[admin]/transaction.js` l. 112–129). Reads after writes throw (`READ_AFTER_WRITE_ERROR_MSG`, l. 113–114). The doc comment says reads "hold a pessimistic lock on all returned documents" (l. 89–92, 130–132).

**Commit.** `Commit` with `transaction = <id>` and the buffered writes (`[admin]/transaction.js` l. 378–404; `[admin]/write-batch.js` l. 468–483). If no read happened, the writes are committed without a transaction id; if there are no reads and no writes, nothing is sent (l. 383–393).

**Rollback.** On any error from the callback or the commit, a `Rollback` RPC is fired without waiting for it: "If there are any locks held, then rollback will eventually release them" (`[admin]/transaction.js` l. 413–446, 499–516).

**Retry.** Up to `maxAttempts` (default `DEFAULT_MAX_TRANSACTION_ATTEMPTS = 5`, `[admin]/index.js` l. 107–111) with `ExponentialBackoff`. Retryable codes: `ABORTED`, HTTP `409`, `CANCELLED`, `UNKNOWN`, `DEADLINE_EXCEEDED`, `INTERNAL`, `UNAVAILABLE`, `UNAUTHENTICATED`, `RESOURCE_EXHAUSTED`, and `INVALID_ARGUMENT` whose message matches `/transaction has expired/`. `RESOURCE_EXHAUSTED` and `409` reset the backoff to its maximum (`[admin]/transaction.js` l. 455–489, 651–689). A retry passes the previous id as `read_write.retry_transaction` (l. 544–546; proto field "An optional transaction to retry", `[proto]/common.proto` l. 63–66).

**Read-only transactions.** `runTransaction(fn, { readOnly: true, readTime? })` (`[admin]/index.js` l. 1013–1027; typings `types/firestore.d.ts` l. 544–559). They get one attempt, no backoff and no write batch (`[admin]/transaction.js` l. 77–81, 457–460), and `commit` / `rollback` are skipped (l. 417, 506). Without `readTime` the first read sends `new_transaction: { read_only: {} }`. With `readTime` no transaction is started at all: every read sends `read_time` directly (l. 532–537).

**Documented semantics** (`[admin]/index.js` l. 956–975): "A read-write transaction obtains a pessimistic lock on all documents that are read … These locks block other transactions, batched writes, and other non-transactional writes", "retried up to five times", "Read-only transactions do not lock documents … may be up to 60 seconds in the past. Read-only transactions are not retried", "Transactions time out after 60 seconds if no documents are read. Transactions that are not committed within than 270 seconds are also aborted."

### 1.2 Client SDK (`@firebase/firestore`)

**No server transaction.** `Transaction.lookup` calls `invokeBatchGetDocumentsRpc` with only `documents` (no `transaction`, `new_transaction` or `read_time`) and records each document's version; a missing document is recorded as `SnapshotVersion.min()` (`[js]/core/transaction.ts` l. 63–76, 118–144; `[js]/remote/datastore.ts` l. 210–227). Reading the same document twice with different versions fails locally with `ABORTED` "Document version changed between two reads." (l. 132–140).

**Preconditions instead of locks** (`[js]/core/transaction.ts` l. 146–195):

| Operation       | Document was read and not yet written                                                                                             | Otherwise       |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------- | --------------- |
| `set`, `delete` | `update_time = <read version>`, or `exists = false` if it was missing                                                             | none            |
| `update`        | `update_time = <read version>`; if it was missing, fails locally `INVALID_ARGUMENT` "Can't update a document that doesn't exist." | `exists = true` |

**Commit.** One `Commit` RPC with only `writes`, no `transaction` field. Every document read but not written gets a `VerifyMutation` with its precondition, so reads that were never written are still checked at commit (`[js]/core/transaction.ts` l. 97–116; `[js]/remote/datastore.ts` l. 194–208). There is no `Rollback`, because nothing is held.

**Reads.** `Transaction.get` takes only a `DocumentReference` (`[js]/lite-api/transaction.ts` l. 90–91). No queries or aggregations in a transaction. Reads after writes fail: "Firestore transactions require all reads to be executed before all writes." (`[js]/core/transaction.ts` l. 66–71).

**Retry.** `maxAttempts`, default 5 (`[js]/core/transaction_options.ts` l. 20–30), with `ExponentialBackoff` on the async queue (`[js]/core/transaction_runner.ts` l. 44–80). Retryable: `aborted`, `failed-precondition`, `already-exists`, and every non-permanent code (`CANCELLED`, `UNKNOWN`, `DEADLINE_EXCEEDED`, `RESOURCE_EXHAUSTED`, `INTERNAL`, `UNAVAILABLE`, `UNAUTHENTICATED`) (`[js]/core/transaction_runner.ts` l. 115–128; `[js]/remote/rpc_error.ts` l. 58–88). The comment explains the extra codes: "the backend will fail outdated reads with FAILED_PRECONDITION and non-matching document versions with ABORTED" (l. 117–118). A synchronous throw from the update function is not retried (l. 96–100).

**Read-only transactions / `readTime`.** `TransactionOptions` has only `maxAttempts` (`[js]/core/transaction_options.ts` l. 27–30). The client has no read-only transaction and no public `readTime` read.

**Offline.** "Transactions will fail when the client is offline." "Batched writes execute even when the user's device is offline." ([Transactions and batched writes](https://firebase.google.com/docs/firestore/manage-data/transactions)). The full SDK sends ordinary writes through the `Write` stream (`[js]/remote/persistent_stream.ts` l. 741, 801); the transaction path above uses unary `Commit`.

### 1.3 Why they differ: the protocol and the database

- **Credential.** "Firestore does not allow 3rd party auth requests to create read-write transactions." (`[proto]/common.proto` l. 60–62, on `TransactionOptions.ReadWrite`). The proto does not say whether read-only transactions are allowed for third-party auth.
- **Database concurrency mode.** "Mobile and web SDKs emulate optimistic concurrency transactions using write preconditions on document versions", and "even if the database concurrency mode is configured for `PESSIMISTIC`, mobile clients still behave optimistically". Server libraries follow the database setting: "Standard edition uses pessimistic concurrency controls", "Enterprise edition uses optimistic concurrency controls by default". It is changed with `gcloud firestore databases update --concurrency-mode` ([Transaction data contention](https://firebase.google.com/docs/firestore/transaction-data-contention)). So "admin = locks" holds only on a `PESSIMISTIC` database.
- **Lock deadline.** A transaction can fail because it "exceeded the lock deadline (20 seconds)" ([Transactions and batched writes](https://firebase.google.com/docs/firestore/manage-data/transactions)).

## 2. Security rules and credentials

- "The server client libraries bypass all Cloud Firestore Security Rules" and should be secured with IAM; "Every database request from a Cloud Firestore mobile/web client library is evaluated against" the rules ([Get started with Security Rules](https://firebase.google.com/docs/firestore/security/get-started)).
- The [REST API page](https://firebase.google.com/docs/firestore/use-rest-api) says it is the token that decides: with a **Firebase ID token** "Cloud Firestore uses Cloud Firestore Security Rules to determine if a request is authorized"; with a **Google Identity OAuth 2.0 token and a service account** "Cloud Firestore uses Identity and Access Management (IAM)", "assumes that your requests act on behalf of your application instead of an individual user", and "allows these requests to ignore your security rules". **Unauthenticated** requests are evaluated against rules too. Both go in `Authorization: Bearer {YOUR_TOKEN}`.
- IAM roles for the bypassing path: `roles/datastore.owner`, `roles/datastore.user` ("Read/write access to data … Intended for application developers and service accounts"), `roles/datastore.viewer`. Rules evaluation itself depends on the service account `service-<project_number>@firebase-rules.iam.gserviceaccount.com` holding `roles/firebaserules.system` ([IAM for Firestore](https://docs.cloud.google.com/firestore/native/docs/security/iam)).
- Rules change query semantics for rules-checked callers only: "security rules are not filters—queries are all or nothing. If a query could potentially return documents that the client does not have permission to read, the entire request fails." ([Securely query data](https://firebase.google.com/docs/firestore/security/rules-query)). Rules also cap document-access calls at "10 for single-document requests and query requests" and "20 for multi-document reads, transactions, and batched writes" ([quotas](https://firebase.google.com/docs/firestore/quotas)).
- **Which credentials the Admin SDK can carry.** `firebase-admin` hands `@google-cloud/firestore` either a service-account key (`credentials: { private_key, client_email }`) or nothing, letting it use Application Default Credentials; any other credential fails with `invalid-credential` (`[fbadmin]/firestore/firestore-internal.js` l. 86–127). Both are Google OAuth 2.0 credentials, so the Admin SDK always bypasses rules.
- **Which credentials the client SDK carries.** An `OAuthToken` that sets `Authorization: Bearer <Firebase ID token>` (`[js]/api/credentials.ts` l. 83–91), nothing when signed out, or, on Google-hosted first-party apps, `X-Goog-AuthUser` / `Authorization` / `X-Goog-Iam-Authorization-Token` (`FirstPartyToken`, l. 407–443). A failed request with `UNAUTHENTICATED` invalidates both the auth and App Check tokens (`[js]/remote/datastore.ts` l. 123–133).
- **Emulator.** With `ssl: false` (set automatically by `FIRESTORE_EMULATOR_HOST`), the Admin SDK adds `Authorization: Bearer owner` "so that the connection is recognized as admin in Firestore Emulator" (`[admin]/index.js` l. 606–613, 1228–1240). The client SDK sends a real or signed-out token, or a `mockUserToken` built by `createMockUserToken` (`[js]/lite-api/database.ts` l. 360–386), so the emulator evaluates rules.

## 3. `readTime` reads

- **Protocol.** Every read RPC has a `consistency_selector` oneof: `transaction`, `new_transaction` (on `BatchGetDocuments`, `RunQuery`, `RunAggregationQuery`, `ExecutePipeline`) or `read_time`. `GetDocument`, `ListDocuments`, `PartitionQuery` and `ListCollectionIds` take `transaction` / `read_time` only (or only `read_time`) (`[proto]/firestore.proto` l. 277–286, 339–348, 462–477, 583–600, 662–679, 746–763, 855–861, 1177–1183). `read_time` "must be a microsecond precision timestamp within the past one hour, or if Point-in-Time Recovery is enabled, can additionally be a whole minute timestamp within the past 7 days". `Listen` targets also take `read_time` (`Target.read_time`, l. 1062).
- **Admin.** Only reachable through `runTransaction(fn, { readOnly: true, readTime })`, which sends `read_time` on each read and opens no transaction (`[admin]/transaction.js` l. 532–537). The Admin doc comment still says "may not be more than 60 seconds in the past" (`[admin]/index.js` l. 933–935), stricter than the proto's one hour.
- **Client.** No public API sends `read_time` on a one-shot read. Every response carries `read_time` (e.g. `BatchGetDocumentsResponse.read_time`, `[proto]/firestore.proto` l. 505), which both SDKs read; the client's `RunQuery` drops responses that only carry a `read_time` (`[js]/remote/datastore.ts` l. 298).

## 4. Transport and `preferRest`

- **Admin.** gRPC by default through `google-gax`. With `preferRest: true` (or `FIRESTORE_PREFER_REST=true|1`), each GAPIC client is built with `fallback: 'rest'` unless the method `requiresGrpc`; currently "the only operation that requires gRPC is creating a snapshot listener" (`[admin]/index.js` l. 476–488, 512–548, 595–603). Only `listen` is bidirectional (l. 1445–1459). `firebase-admin` passes `preferRest` through and refuses to reinitialize with a different value (`[fbadmin]/firestore/firestore-internal.js` l. 67, 89–118).
- **Client.** The browser uses REST (`fetch`/XHR) for unary RPCs and WebChannel for `Listen` / `Write` (`[js]/remote/rest_connection.ts`, `[js]/platform/browser/webchannel_connection.ts`). The Node build uses gRPC (`[js]/platform/node/grpc_connection.ts`).
- **Protocol.** `Write` and `Listen` are "only available via gRPC or WebChannel (not REST)" (`[proto]/firestore.proto` l. 204–220). Everything else, `BeginTransaction`, `Commit`, `Rollback`, `BatchGetDocuments`, `RunQuery`, `BatchWrite`, has a REST binding (l. 98–126, 246–251).
- **Connection pool.** The Admin SDK opens more GAPIC clients past 100 concurrent requests per channel, "as enforced by Google's Frontend" (`[admin]/index.js` l. 116–122), and retries non-transactional idempotent requests up to `MAX_REQUEST_RETRIES = 5` (l. 103–106, 1301–1321).

## 6. Limits and write paths

- **Writes per commit.** "Firestore no longer limits the number of writes that can be passed to a Commit operation or performed in a transaction" (previously 500), release note of March 2023 ([Firestore release notes](https://docs.cloud.google.com/firestore/docs/release-notes)). Neither SDK enforces a count client-side; the client SDK doc comments still state 500.
- **Remaining limits** ([quotas](https://firebase.google.com/docs/firestore/quotas)): 10 MiB API request size; 270 s per transaction with a 60 s idle expiration; 500 field transformations per document per `Commit` or transaction; rules document-access calls 10 / 20 (rules-checked callers only).
- **Admin-only write paths.** `BulkWriter` uses the non-atomic `BatchWrite` RPC ("does not apply the write operations atomically … does not allow more than one write per document", `[proto]/firestore.proto` l. 236–251) in batches of 20 (10 on retry), throttled by the 500/50/5 rule from 500 up to 10,000 ops/s (`[admin]/bulk-writer.js` l. 16–55). `WriteBatch.commit()` retries `ABORTED` (`[admin]/write-batch.js` l. 439–447). `create()` sends `exists = false` (l. 164). Bulk work is meant for server libraries: "You should use a server client library for bulk data operations and not a mobile/web SDK" ([Transactions and batched writes](https://firebase.google.com/docs/firestore/manage-data/transactions)).
- **Client write path.** Full SDK: the `Write` stream with the local mutation queue, so writes apply locally first and survive offline (`[js]/remote/persistent_stream.ts` l. 741–801). Lite SDK and transactions: unary `Commit`.

## 7. How this repo wraps them today

- The portable `Firestore.TransactionOptions` has only `maxAttempts` (`packages/effect-firebase/src/firestore/Firestore.ts` l. 175–181). Read-only transactions and `readTime` are not exposed, even on the admin side.
- `AdminFirestore` and `ClientFirestore` both build `runTransaction` with `Firestore.transactionFromCallback`, handing the options straight to `firestore.runTransaction` / `Client.runTransaction` (`packages/admin/src/firestore/internal/firestore.ts` l. 224–236; `packages/client/src/firestore/internal/firestore.ts` l. 232–233). The locking vs optimistic difference is inherited from the SDKs and is not visible in the service.
- `AdminFirestore.Options` exposes `preferRest`, passed to `initializeFirestore` only when set (`packages/admin/src/firestore/internal/firestore.ts` l. 24–33). `ClientFirestore.Options` exposes `localCache` and `emulator` (host and port, no `mockUserToken`) (`packages/client/src/firestore/internal/firestore.ts` l. 24–36).
- The in-memory engine retries a conflicting transaction up to `maxAttempts` (`packages/effect-firebase/src/firestore/internal/memory.ts` l. 302–343), which is the optimistic model.

## Implications for the native engine

- The transaction strategy is a function of the credential and the database, not of the transport. A Firebase ID token or no token cannot open a read-write server transaction, so that path needs the optimistic emulation: plain reads, versions recorded, `update_time` / `exists` preconditions and `verify` writes on `Commit`. A Google OAuth2 credential can use `new_transaction` on the first read, `transaction` on later reads and the commit, `retry_transaction` on retry, and `Rollback`. Whether that server transaction actually locks depends on the database's concurrency mode, which the engine cannot see from the request.
- Both strategies share the outer loop: up to 5 attempts, exponential backoff, rerun the body. They differ in which codes count as retryable.
- Queries and aggregations inside a transaction, read-only transactions and `read_time` reads exist on the wire for every read RPC; today only the Admin SDK reaches them. The proto restricts only read-write transactions for third-party auth; it does not say whether an ID token can open a read-only transaction or send `read_time`. That needs an experiment.
- Rules bypass is entirely the bearer token: the same RPC is rules-checked with an ID token and IAM-checked with a service-account token. Rules-checked callers also get "all or nothing" queries and the 10/20 document-access caps; IAM callers do not.
- The emulator needs `Authorization: Bearer owner` for admin behaviour, or a mock user token for rules behaviour; it is a credential choice.
- Per-caller headers: client identity (`X-Firebase-GMPID`, `x-firebase-appcheck`, API key) goes with the client credential set; `google-cloud-resource-prefix` and `x-goog-request-params` go on every request, in whichever format each transport uses; `x-goog-api-client` identifies the library.
- `Listen` and `Write` have no REST binding. A REST-only transport cannot listen or use the write stream; the Admin SDK's `preferRest` falls back to gRPC for `Listen`, and the browser uses WebChannel.
- No client-side write-count limit is required by the server any more; the 10 MiB request size and the transaction time limits remain.
- `BatchWrite` (non-atomic, one write per document) is a separate RPC from `Commit` and is what bulk writing is built on.

## Not settled

- Whether a Firebase ID token may open a **read-only** transaction (`new_transaction: { read_only: {} }`) or send `read_time` on reads. The proto only forbids read-write transactions for third-party auth.
- Whether `retry_transaction` changes lock priority on the server. The proto only calls it "an optional transaction to retry".
- Whether the server's optimistic mode (Enterprise / `OPTIMISTIC`) uses the same `ABORTED` / `FAILED_PRECONDITION` codes as the client's precondition emulation; the docs only say contention ends in `ABORTED`.
- The exact date of the 500-write removal: the fetched release notes page dates the entry March 29, 2023; a search snippet said March 24, 2023.
