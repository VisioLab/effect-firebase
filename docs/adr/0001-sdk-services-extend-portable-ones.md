# SDK services extend the portable ones

The core package's `Firestore` is the strict intersection of the Admin and client SDKs, so portable code written against it runs on either. What only one SDK can do lives in that SDK package, in a service that extends the portable one, the way `@effect/sql-pg`'s `PgClient` extends `SqlClient`. For example, `AdminFirestore extends Firestore`. An SDK's `layer` provides the same object under both tags, so portable code and SDK-specific code can share one database.

An SDK service only ever widens the portable one. It may add methods for capabilities the portable one lacks, add optional options to existing methods, return richer types (a `ClientDocumentSnapshot` with metadata), and exclude more requirements. It never adds required parameters, errors or requirements to an existing method, and it never adds a parallel variant of one (no `streamDocWithMetadata`). That keeps every SDK service's object usable as its portable one.

The SDK service's _type_ is still not a subtype of the portable one, following Effect's own fix for `PgClient` and `SqlClient` (Effect-TS/effect#10387). A service type is also its requirement identifier, and `Exclude<R, Firestore>` drops every subtype of `Firestore`. If `AdminFirestore` were one, providing a portable `Firestore` layer alone, such as an in-memory fake built with `Firestore.make`, would remove `AdminFirestore` from an effect's requirements, and the program would type-check and then fail with "Service not found". So:

- The portable types carry a brand: `Firestore` and `Transaction` each have a type id property that `Firestore.make` sets.
- An SDK service type extends the unbranded `Firestore.With`, not `Firestore`, and its key adds the portable type back as the service shape: `Context.Service<AdminFirestore, AdminFirestore & Firestore>`. What `yield* AdminFirestore` hands back, and what `make` returns, is both.
- An SDK transaction service type extends the unbranded `Firestore.TransactionBase`, not `Transaction`, and its key adds the portable transaction back: `Context.Service<AdminTransaction, AdminTransaction & Transaction>`. A body that asks for it through the portable `Firestore` still needs it provided, and `Firestore.With`'s `TransactionServices` parameter lists it so the SDK's own `runTransaction` drops it.
- Every SDK service and SDK transaction type carries a type id of its own too, set where the SDK assembles it. A brand only keeps two types apart when both have one: a type with no brand and the same members would still absorb a branded one.

A module's main type or a service takes an SDK prefix (`AdminFirestore`, `AdminTransaction`, `ClientDocumentSnapshot`) exactly when it extends a portable type, because that is when both live side by side in one program and plain names would be ambiguous. Other types inside a prefixed module keep plain names even when they extend a portable type: `ClientDocumentSnapshot.Existing` and `.Missing` extend the portable variants, but the module already carries the prefix wherever they're used. `AdminTransaction` keeps its prefix even though it lives in `AdminFirestore`, because services appear unqualified in an effect's requirements and type hovers, where `Transaction | Transaction` would be ambiguous. A module that maps between a portable module's values and an SDK's (`AdminFirestoreValue`, `ClientFirestoreValue`) takes the prefix too: it extends nothing, but it is that SDK's counterpart of the core `FirestoreValue`, both are imported side by side wherever a raw SDK write is encoded, and a plain name would collide with it. Types with no portable counterpart (`App`, `Auth`) keep their plain name.

## Considered Options

- **Same names with their own keys** (`Firestore` in every package, told apart by namespace import), following `App`. Rejected because `Firestore` would mean two things in any file that touches both.
- **A side-car service** holding only the SDK extras next to an untouched `Firestore`. Rejected: it splits one database into two services, and SDK methods could no longer share the portable ones' mapping to and from Firestore Values and their error mapping.
- **SDK services as subtypes of the portable ones, accepting the gap.** What this ADR first chose, since the SDK layers always provide both tags. Rejected once Effect closed the same gap for its SQL drivers: it is easy to hit with a test fake, and it fails only at runtime.
- **A class-style key for `AdminTransaction`**, whose identifier is the class rather than the transaction type. It closed the gap for transactions alone, made the transaction's own type `AdminTransaction["Service"]`, and left `AdminFirestore` with the gap.
- **Only an escape hatch to the raw SDK instance.** Kept as a field on the SDK services, but rejected as the whole answer, since it gives up schemas and typed errors for everything it touches.
